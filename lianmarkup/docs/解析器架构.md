# 解析器架构

写这篇文章的时候解析器已经能跑了, 我回头一看, 发现它和我去年设想的"先造 Lfsm/Lpda 框架再写解析器"完全不一样 —— 根本没有状态机框架, 就是朴素的 if-else 分派加递归。

但我一点也不失望, 反而想明白了一件事: **好解析的语法是设计出来的, 不是解析器硬扛出来的**。语法规范里那几条"保命规则"(行首关键字必须带空格、定界符必须成对、解析失败回退正文)把歧义在设计阶段就消灭了, 解析器自然不需要复杂的 lookahead 和回溯。

> 所以 `if else` 真的是一个非常伟大的发明 —— 我在 [如何读取文本流.md](./如何读取文本流.md) 里就说过这话, 现在它成了整个块级解析的骨干。

---

## 0x00 总体形状

```
parse(&str) -> Document { html, toc, notes }
```

纯函数, 无 IO, 永不报错。任何无法匹配的内容都回退为正文段落, 不存在"解析失败"这种状态。

解析分两个阶段, 顺序不能反:

1. **块级** (`src/block.rs`): 按行切分, 看行首决定这一行是什么块
2. **行内** (`src/inline.rs`): 在块的内容里二次扫描, 处理 `**`、`[^` 这些

块级先行意味着行内符号永远不会干扰块结构 —— 段落里写一个 `>` 不会变成引用块, 因为它不在行首。

## 0x01 块级: 行首分派

`parse_blocks` 的骨干就是一条 if-else 链。主循环先跳过空行和 `//` 注释行, 然后按优先级尝试每种块级语法:

```text
``` 围栏代码 → ~~~ 原样块 → ::: 示例块 → $$ 公式块 → >>> 折叠块 → callout 家族
→ > 引用块 → # 标题 → --- 分割线 → @toc 指令 → 列表 → 表格 → 段落(兜底)
```

每个分支自己做两件事: 吃掉属于它的行, 吐出 HTML。吃行的时候返回下一个未消费的行号, 主循环接着走。

容器类的块(折叠块、callout、引用块)收到的内容是**递归调用 `parse_blocks`** 处理的, 所以折叠块里可以放代码块、可以放 callout, 不用写任何额外代码。这是我最喜欢的部分 —— 组合是免费的。

> 折叠块的两种模式在 `>>>` 那一行就一次性判定完毕: 下一行以 TAB 开头就是缩进作用域模式, 否则就是显式配对模式。判定之后互不跨界, 状态机只有一个比特的状态。

## 0x02 行内: 配对扫描

行内解析把文本转成 `Vec<char>` 从头扫到尾, 遇到可能的定界符就尝试**找配对**:

- `find_close` 从当前位置往后找未转义的闭合定界符
- 找到了且内容非空 → 生成标签, 内容递归 `parse_inline` (所以 `**粗里有*斜***` 也能对)
- 找不到或内容为空 → 这个符号原样输出为文本, 继续往下走

这就是回退规则的实现: 不需要预判, 不需要回溯, 失败了就当文本。`2*3=6` 里的 `*` 找不到配对, 自动是文本。

几个有特殊规则的家伙:

| 语法 | 特殊处理 |
|-|-|
| `***...***` | 先于 `**` 尝试, 渲染 `<strong><em>` 嵌套 |
| `[^...]` / `[...]{...}` | 闭合 `]` 按方括号深度配对 (内容里可能嵌链接) |
| `[...]{.class}` | `{` 首字符是 `.` 才算类名, 参数变 CSS 自定义属性; 否则回退文本 |
| `$...$` | 内容首尾不能是空格、不含换行 (不然 `$5 和 $6` 会被当成公式) |
| 图片属性 `{}` | 里面含 `=` 才按属性消费, 不然可能是 `{#id}` 或注音 |
| `\` | 只对语法符号生效, 后面跟普通字符时原样保留 |

## 0x03 状态的归宿

解析过程只有一点点状态, 全在 `Parser` 结构体里:

- `heading_count`: 标题编号, 生成 `h-N` 锚点
- `headings`: 扁平的标题列表, 最后组装成 TOC 树
- `note_count` / `notes`: 旁注编号和内容
- `toc_depth`: `@toc depth=N` 指令设置的收集深度

TOC 树的组装在 `build_toc`: 递归地把扁平列表按级别归拢, 比当前级别深的就收为 children。

## 0x04 文件地图

```
src/
├── lib.rs      # 入口 parse(), 产物结构, front matter 剥离, TOC 组装
├── block.rs    # 块级: 行首分派 + 各种块的解析
├── inline.rs   # 行内: 配对扫描 + 各种行内语法
└── escape.rs   # HTML 转义
```

测试全是黑盒的, 只走公开的 `parse` API: `tests/syntax.rs` 覆盖每种语法和回退场景, `tests/first_post.rs` 拿 `examples/first-post.ly` 做端到端。

## 0x05 性能怎么看

块级几乎零拷贝, 全程 `&str` 切片; 行内因为要按字符扫描(中文字符是多字节的, 按字节切会碎), 收了一层 `Vec<char>`。博客文章撑死几万字, 渲染期解析一次, 这个量级根本不需要优化。

真要较劲的时候, 优先把行内的 `Vec<char>` 换回字节索引加 `char_indices`, 但我觉得那一天可能永远不会来。
